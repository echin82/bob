## 1. Summary

The Contract Risk Assessment Tool is a single-user, single-screen web application for sales and legal desk users. A user uploads a contract file (PDF or DOCX), the system simulates risk analysis and produces a structured report, and the user reviews and annotates individual findings — all without leaving the page and with full persistence across browser restarts.

The MVP is scoped for local demo use on a single machine. There are no external services, no authentication, no real document parsing, and no AI integration. Risk reports are generated by a mock engine with predefined clause rules. All persistence is handled by a single SQLite file.

The plan covers the six components defined in the architecture, their boundaries, the data they own, and the decisions and risks that bear on build readiness.

## 2. Technical Context

| Dimension | Detail |
|-----------|--------|
| **Deployment target** | Single machine, localhost only |
| **Frontend** | React single-page application (SPA) |
| **Backend** | Node.js process (Express or equivalent) |
| **Persistence** | SQLite (`data.db`), single file |
| **File storage** | Local `uploads/` directory, files keyed by contract ID |
| **Real-time updates** | Server-Sent Events (SSE), server → browser, one-directional |
| **Document intelligence** | Simulated; no file content is parsed |
| **Authentication** | None — single-user, no session management |
| **External APIs** | None |
| **Concurrency** | Single user; no concurrent-write requirement |

The backend process hosts the REST API, the SSE endpoint, and the Risk Engine module within the same Node.js process (AD-2). There is no microservice boundary and no inter-process communication.

## 3. Components and Boundaries

### 3.1 React Frontend

**Owns:** all presentation, user interaction, client-side validation, SSE subscription, and local risk-level recalculation.

**Boundaries:**
- Validates file format and size in the browser on selection (first gate), before any upload request is sent.
- Subscribes to the SSE stream and updates the queue in-memory without a page reload.
- Renders the report inline within the same screen; no separate route or URL change (AD-6).
- Paginates findings locally at 10 per page from the full findings list returned by the API (NFR-7).
- Recalculates and displays the overall risk level locally from the in-memory findings state each time a finding status changes (AD-3).
- On initial page load, fetches the full contract list and any open report from the backend; holds no persistent state of its own.

**Does not own:** report generation logic, file persistence, database reads or writes.

---

### 3.2 REST API Layer

**Owns:** HTTP surface area, file I/O orchestration, contract and report data serving, finding update persistence, and SSE stream management.

**Boundaries:**
- Re-validates format and size server-side before any write occurs (second gate, AD-5).
- Writes the uploaded file to the local file store and creates the contract record in SQLite before returning the upload response.
- Triggers the Risk Engine asynchronously after a successful upload; the response to the browser does not wait for generation to complete.
- Serves the contract list, individual report, and findings on request.
- Accepts `PATCH` requests for finding status and comment updates; writes changes to SQLite.
- Manages the SSE connection and emits the `pending → complete` event when notified by the Risk Engine.

**Does not own:** report generation logic (Risk Engine), risk-level recalculation (frontend).

---

### 3.3 Risk Engine

**Owns:** simulated report generation — findings, severity labels, section references, overall risk level, and summary.

**Boundaries:**
- Receives a contract ID from the API layer after a successful upload.
- Generates a deterministic set of mock findings from a fixed set of predefined clause rules (A1, A5). Does not read file content.
- May apply an artificial delay to simulate realistic async processing; total upload-to-report time must remain within 10 seconds (NFR-1, R-2).
- Writes the completed report, findings, and `complete` status to SQLite, then signals the SSE layer.
- Exposes no HTTP endpoint; called only by the REST API layer.

**Does not own:** HTTP handling, file storage, SSE connection management.

---

### 3.4 SQLite Database

**Owns:** all persisted business state — contracts, reports, findings, finding statuses, and comments.

**Boundaries:**
- Accessed only through the backend; the frontend has no direct database connection.
- Write-once from the Risk Engine for report data; reading and finding updates go through the REST API layer.
- Single-file (`data.db`), collocated with the backend process.

---

### 3.5 Local File Store

**Owns:** raw uploaded file bytes on disk.

**Boundaries:**
- Files are written once at upload time, named by contract ID to avoid collisions.
- The MVP does not serve file downloads or support file deletion.
- Location is a relative path from the backend working directory (R-4).

---

### 3.6 SSE Endpoint

**Owns:** the open HTTP connection from server to browser for live status events.

**Boundaries:**
- One-directional: server → browser only. The frontend sends no data over this channel.
- Emits a single event type: status change (`pending → complete`) for a given contract ID.
- Must deliver the event to the browser within 3 seconds of the Risk Engine writing the `complete` status to SQLite (NFR-2).

## 4. Interfaces and Integrations

All communication is local (no network egress). There are three interaction channels:

### 4.1 Frontend ↔ REST API (HTTP)

Used for:
- File upload (multipart POST)
- Contract list retrieval on page load
- Report and findings retrieval when a user opens a completed contract
- Finding status and comment updates (PATCH per finding)

The upload response returns the new contract metadata immediately so the queue entry appears before report generation completes.

### 4.2 Frontend ← SSE Endpoint (Server-Sent Events)

Used for:
- Pushing `pending → complete` status change events to the browser

The frontend subscribes on page load and holds the connection open. On receiving an event, it updates the matching queue entry in-memory. No polling fallback is required for the MVP.

### 4.3 REST API → Risk Engine (in-process call)

Used for:
- Triggering asynchronous report generation after a successful upload

The call is non-blocking from the API's perspective; the Risk Engine writes its output directly to SQLite and signals back to the SSE layer when done. There is no response value returned to the API layer.

## 5. Data Model Summary

Three logical entities cover all persisted state. Schema detail is deferred to implementation.

### Contracts

One row per uploaded file.

| Field | Purpose |
|-------|---------|
| Contract ID | Internal unique identifier; used as the file name key in the file store |
| File name | Original file name shown in the queue |
| Upload timestamp | Shown in the queue; used for display ordering (R-5) |
| Processing status | `pending` or `complete`; drives queue display and SSE events |

### Reports

One row per contract (created when the Risk Engine completes).

| Field | Purpose |
|-------|---------|
| Contract ID (FK) | Links the report to its contract |
| Overall risk level | Categorical label (`Low`, `Medium`, `High`, `Reviewed`); stored as generated; display value recalculated in the frontend |
| Summary | Short free-text summary produced by the mock engine |

### Findings

One row per finding within a report (multiple per contract).

| Field | Purpose |
|-------|---------|
| Finding ID | Internal unique identifier for PATCH routing |
| Contract ID (FK) | Groups findings by report |
| Severity | `High`, `Medium`, or `Low`; determines sort order and visual treatment |
| Explanation | Short descriptive text of the risk |
| Section reference | Simulated contract section label (e.g., "Clause 7.2") |
| Status | `null` (unreviewed), `accepted`, `overridden`, or `reviewed`; set by the user |
| Comment | Free-text annotation added by the user; auto-saved on blur |

**Overall risk level recalculation rule (A7):** Derived by the frontend from current finding statuses. Any unreviewed `High` finding → `High`. No unreviewed `High` but at least one unreviewed `Medium` → `Medium`. Only unreviewed `Low` findings remain → `Low`. All findings have a status set → `Reviewed`. Both `accepted` and `overridden` are treated as reviewed for this calculation.

## 6. Key Decisions and Rationale

| ID | Decision | Rationale | Spec trace |
|----|----------|-----------|------------|
| AD-1 | SSE for status updates instead of polling | Delivers the `pending → complete` event immediately; no polling interval to tune. Simpler than WebSockets for a one-directional push. The open connection cost is negligible for a single-user MVP. | FR-4, NFR-2 |
| AD-2 | Risk Engine as an in-process module | Simulated processing has no real computation load. A separate service would add deployment complexity with no benefit at MVP scale. API and Risk Engine share one failure domain, which is acceptable for demo use. | A1, A4, NFR-6 |
| AD-3 | Risk level recalculated in the frontend | All required data (findings + current statuses) is already in the frontend after the report loads. A server round-trip would add latency incompatible with the 2-second NFR-8 budget. The recalculation rule is fully specified in A7. | FR-13, NFR-8, A7 |
| AD-4 | SQLite as sole persistence layer | Satisfies FR-11 (zero data loss across restarts) with no additional server process, matching the single-machine, single-user scope. | FR-11, NFR-5, A2, A3 |
| AD-5 | Dual-gate file validation (client then server) | Client-side validation provides immediate rejection feedback within the 2-second NFR-4 budget. Server-side re-validation prevents invalid files from being persisted if the client check is bypassed. | FR-1, NFR-3, NFR-4 |
| AD-6 | Inline report rendering, no routing | FR-8 and its acceptance criterion explicitly require that the report opens without navigating to a different page or URL. No router or separate view is introduced. | FR-8 |

## 7. Risks and Assumptions

### Assumptions carried from the spec and architecture

| # | Assumption | Impact if wrong |
|---|------------|-----------------|
| A1 | Document intelligence is simulated; the Risk Engine generates mock findings without reading file content. | If real parsing is added later, the Risk Engine boundary must expand significantly. No impact on MVP. |
| A2 | No authentication or multi-user isolation is required. | Any addition of auth would require session management, user-scoped data, and new API surface area. |
| A3 | File storage is local to the machine. No cloud storage is needed. | Cloud storage would require a new integration boundary and credentials handling. |
| A4 | An artificial processing delay is acceptable to simulate async behaviour. | If no delay is used, the upload-to-report transition may appear instantaneous and reduce demo realism. |
| A5 | The predefined mock risk rules are fixed at implementation time and do not affect acceptance criteria. | The demo scenario depends on having recognisable clause types; see R-1 below. |
| A7 | The overall risk level recalculation rule is fully defined (see Section 5). | Any change to the recalculation logic requires updating only the frontend implementation. |
| A8 | Comments auto-save on blur; no explicit save button is shown. | If users expect a save action, the UX will feel unfamiliar. Design is aligned with this assumption. |

### Open items requiring resolution before build

| # | Item | Risk if unresolved | Owner |
|---|------|--------------------|-------|
| R-1 | The specific mock risk rules (clause types, severities, section references) are not yet agreed. | Demo scenario cannot be scripted or validated without knowing what findings will appear. | Product Owner |
| R-2 | The artificial processing delay value is not specified. Must remain within the 10-second NFR-1 budget while feeling realistic. A 2–4 second range is suggested pending confirmation. | If set too high, NFR-1 is violated. If omitted, the demo loses credibility as a simulation. | Tech Lead |
| R-3 | All findings for a report are fetched in a single request and paginated in the frontend. A small fixed mock count is assumed. If the count grows significantly, this approach needs revisiting. | Low risk for MVP given the fixed mock data, but worth confirming a maximum finding count before implementation. | Tech Lead |
| R-4 | The `uploads/` folder path is relative to the backend working directory. Not yet confirmed as sufficient for portability requirements. | If the application must be portable across machines without configuration, a config option may be needed. | Tech Lead |
| R-5 | The contract queue display order is not specified in the spec. Most-recently-uploaded first is assumed. | Incorrect ordering would be visible to demo observers. Needs Product Owner confirmation before the queue component is built. | Product Owner |
